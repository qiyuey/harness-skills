# 七大 harness 维度：评分细则

本文件是 `harness-review` 的评分细则。SKILL.md Step 4 评分前必须 Read 本文件。

每个维度对应一种典型 LLM 工作流失败模式。逐维给 ✅ PASS / ❌ FAIL。

---

## 维度 A：中间状态持久化（Intermediate-State Persistence）

**问题**：每一步执行完后，是否有**持久化 sidecar**（JSON / Markdown 片段 / 子目录）能让外部脚本/下次会话读到本步成果？这是 harness 工程的核心——状态不能只活在 LLM 上下文里。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 每个 Step/Task 都至少落一个**结构化 sidecar**（非 LLM 自由文本），字段定义明确 |
| ❌ FAIL | 以下任一：仅终态文件落盘、中间 Step 全在 LLM 上下文中传递、整个流程无任何分段中间产物 |

**反例**：
> "Step 3 提取分部数据"——只写"读出后填进某 dict 字段"，没说什么时候写盘、字段格式、缺失时怎么办（状态只活在 LLM 上下文里）

---

## 维度 B：断点续做（Resume-After-Interrupt）

**问题**：上次会话执行到第 4 步崩了，**这次会话能不能自动识别"已完成 Step 1-3"并从 Step 4 继续**，而不是从头再来？

| 等级 | 标志 |
|------|------|
| ✅ PASS | 有 manifest/status 命令（如 `<run-manifest> status`）扫描产物推断状态，**不依赖手动维护的状态文件** |
| ❌ FAIL | 以下任一：没有续做概念、重跑等于覆盖、仅靠"如已存在则跳过"的隐式约定而无统一状态查询入口 |

**反例**：
> 一气写完一个长 markdown，token 用尽就要从头再来（无 manifest 脚本，无法识别已完成步骤）

---

## 维度 C：部分重做（Partial Re-do）

**问题**：用户发现"Step 7 的 summary 写得不好，重跑 summary 就行"——能不能**只重跑这一步**而不动其他产物？

| 等级 | 标志 |
|------|------|
| ✅ PASS | SKILL.md 有"重做 X 步：删除 Y 文件"的明确表格，重做粒度 = 单个 Step |
| ❌ FAIL | 以下任一：没有部分重做概念、重做粒度只到整轮（`--force` 全重跑）、无"删除哪些文件触发哪步重做"的对应说明 |

**正例**：给出"删除哪些文件触发哪步重做"的对应表格，并注明跨 Step 联动（如"重做 Step 4 需联动 Step 5"）

---

## 维度 D：程序化 QC（Fast Programmatic QC，含依赖边界）

**问题**：每步完成后，能不能用**纯脚本（非 LLM）**在 10 秒内验证产出合规？包括字段完整性、加总一致、单位、枚举值等机械检查。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 关键 Step 都有配套 QC 脚本，退出码语义清晰，输出可机读；每个 QC 脚本只读取当前 Step 产物或显式声明的上游依赖；脚本命名与 Step 粒度一一对应；SKILL.md 无"禁止在 X 时机运行 Y"的警告语 |
| ❌ FAIL | 以下任一：只有 LLM 自检 checklist 无脚本、只在终态有 QC、QC 覆盖率不足、退出码语义未定义、完全靠人眼或 LLM 复读；联合 QC 存在（脚本跨读多个 Task 产物）；SKILL.md 中出现"禁止在 X 时机运行 Y"类警告语；QC 脚本命名或职责混合多个 Step |

**关键判断**：QC 覆盖的是"有没有脚本"，不是"LLM 自检 checklist"。

**文档-实现脱节是 D 维度的最高风险缺口**——SKILL.md 注释描述了某检查规则，但对应脚本里根本没有实现，等于零保障。典型例子：注释写了某渲染规则，但对应检查函数完全没有覆盖该场景。Step 5 实测是发现这类脱节的最可靠方法。

**QC 依赖边界**：每个 QC 脚本是否只依赖**单个 Task 的产物**，不跨 Task 读取？跨 Step 的联合 QC 会制造两个问题：一是 Step A 结束后没有即时反馈窗口，Step A 的错误要等 Step B 完成才暴露；二是文档不得不补写"禁止在某时机运行"的警告，把时序约束从结构层降级到人工记忆。

**核心原则**：文档里出现"禁止在 X 时机运行 Y"是结构缺陷的信号。约束应当编码进 QC 脚本的输入声明（找不到依赖文件直接失败），而非依赖人工记忆。

**检查方法**：
```bash
# 检查 QC 脚本是否跨 Task 读取产物（文件读取模式按目标语言调整）
grep -rn "<file-read-pattern>" <qc-sources>
# 检查 SKILL.md 是否有时机警告语
grep -n "禁止在.*时机\|禁止在.*运行\|不.*时候.*运行" SKILL.md
```

**反例（联合 QC）**：
> 某联合 QC 同时读取 Step A 产物和 Step B 产物。Step A 结束时 Step B 产物不存在，脚本要么报错要么跳过检查，导致 Step A 的错误要等 Step B 完成后才暴露。SKILL.md 不得不写"禁止在 Step A 末尾运行此脚本"来补救。

**改进建议模板（依赖边界）**：
- 发现联合 QC → 按 Step 边界拆分：每个 QC 只服务一个 Step 的即时反馈窗口
- 下游 Step 的 QC 如需交叉验证上游产物，可以读取上游产物，但须在脚本入口声明依赖并在文件缺失时给出明确报错
- 删除 SKILL.md 中一切形如"禁止在 X 时机运行 Y"的警告——结构正确后这种警告就不需要存在

**⚠️ 结构代码味信号：步骤小数编号**

Step 编号中出现小数（Step 9.5）或字母后缀（Step 9b）是流程被打补丁的信号——通常意味着原作者发现新增逻辑无处安放，临时塞进两个相邻 Step 之间。这会污染 manifest 扫描、引诱后续作者继续叠加补丁。发现时在维度 D 的改进建议里一并提出。

**改进建议模板（步骤编号）**：
- 若发现 Step X.5 → 选项 A：升格为 Step X+1，后续 Step 全部 +1 重新编号；选项 B：作为 Step X 的子步骤，明确不是独立顶层步骤
- 若该 Step 有独立产物/QC 脚本/manifest 扫描需求 → 必须升格为整数顶层 Step

## 维度 E：可观测性 / Audit Trail（Observability）

**问题**：维度 A-D 解决"能不能恢复"，本维度解决**"事后能不能查为什么"**。当下游用户报告"某数据看起来不对"，能否追溯到具体哪一步、哪一次 LLM 调用、引用了哪个外部源？

| 等级 | 标志 |
|------|------|
| ✅ PASS | 每个 sidecar 都有 `generated_at` (ISO timestamp) + `source` / `inputs_hash` / `tool_versions` 等溯源字段；外部素材（PDF、网页）落盘在 `_sources/` 子目录 |
| ❌ FAIL | 以下任一：任何 sidecar 缺少时间戳或来源字段、只有终态产物有时间戳而中间 Step 无记录、引用外部素材但不存快照、事后无法 reproduce |

**反例**：
> 调用外部 API 抓取某数值写入产物，但不记录抓取时间——事后用户问"这个值是什么时候的"，无从查起

---

## 维度 F：失败处理契约（Failure-Handling Contract）

**问题**：Step 3 超时/校验失败/外部 API 返回空/QC 退出码 1 时，**SKILL.md 是否明确写了下一步怎么办**？是重试一次？整轮中止？降级到默认值继续？没有契约的话，LLM 会即兴发挥——这本身就是反 harness。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 关键失败点（外部数据缺失、QC 不过、用户中断）都有"如果 X 则 Y"的显式契约；QC 脚本退出码语义有定义（例如 exit=1 数值不符 / exit=2 schema 缺字段 / exit=3 违反硬约束） |
| ❌ FAIL | 以下任一：整个 SKILL.md 找不到"失败"/"错误"/"重试"/"中止"等措辞、QC 失败或外部依赖失败无处理契约、退出码语义未定义 |

**反例**：
> "用某数据源取数据"——不说取不到时降级到备用源还是中止；LLM 一遇错就乱猜数字

---

## 维度 G：指令正向性（Instruction Polarity）

**问题**：SKILL.md 中的**行为/风格类负向约束**（"禁止"、"不要"、"不得"）是否过多？根据 arXiv:2511.12381（2025年11月），LLM 处理负向指令时会先在内部激活被禁止的概念再尝试抑制——抑制失败时，被禁止的行为反而更容易出现（「反讽回弹效应」）。

**关键区分：两类负向指令，处理方式不同**

| 类型 | 例子 | 处理方式 |
|------|------|---------|
| **行为/风格约束**，有正向等价 | "禁止用某语言"、"不要写文件"、"不评估领域质量" | 改为正向表达，消除回弹风险 |
| **内容边界约束**，无正向等价 | "禁止在 section X 写入 Y 类内容" | 允许保留负向，但**必须有对应 QC 脚本强制执行**；若无 QC 配套 → 视为维度 D FAIL（文档-实现脱节） |

内容边界约束描述的是"这个 section 不归属此类内容"，没有等价的正向写法，因此允许保留负向。但仅靠文档说明是不够的，必须有 QC 脚本能在产物生成后自动检出违规。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 行为/风格类约束均以正向表达；内容边界类负向约束均有对应 QC 检查项 |
| ❌ FAIL | 以下任一：存在行为/风格类负向约束（有正向等价但未改写）；出现语言禁令；内容边界类负向约束无 QC 配套 |

**检测方法**：
```bash
# 统计所有负向约束行
grep -n "禁止\|不要\|不得\|不允许\|避免\|don't\|do not\|never\|must not" SKILL.md

# 对每条负向约束判断：是行为/风格约束（有正向等价）还是内容边界约束（无正向等价）
# 对行为/风格约束：提供正向改写建议
# 对内容边界约束：grep 对应 QC 脚本是否有实现
```

**行为/风格约束正向改写参考**：
| 负向写法（有回弹风险）| 正向改写 |
|---|---|
| 禁止用某语言 | 所有输出使用目标语言 |
| 不要写文件 | 将结果输出到对话 |
| 不评估领域质量 | 评估范围限于 harness 工程质量 |
| 避免空泛断言 | 每个 finding 引用 SKILL.md 具体行号 |
| 不允许降级 | 严格执行强制路径 |
