# harness 审计维度：评分细则

本文件是 `harness-review` 的评分细则。SKILL.md Step 4 评分前必须 Read 本文件。

## 两层结构：方法论基本面 → 审计维度

harness 方法论可以浓缩成**六个基本面**——这是给人理解的思想骨架。但审计要逐条机械打分，颗粒必须更细：每个基本面分解成一个或多个**审计维度**，按"检查对象"切分，保证彼此**互斥不重叠、合起来不遗漏**（MECE）。所以"基本面是 6 个、审计维度更多"不是矛盾，而是金字塔的两层。

| 方法论基本面（思想）| 审计维度（逐条打分）|
|---|---|
| 1 契约先于实现 | F 失败处理契约 |
| 2 状态必须落盘 | A 中间状态持久化 |
| 3 质检要程序化 | **D1** QC 存在性与覆盖率 · **D2** QC 依赖边界 · **D3** 指令极性 |
| 4 失败要能局部恢复 | **B** 断点续做 · **C** 部分重做 |
| 5 过程要可审计 | E 可观测性 / Audit Trail |
| 6 流水线要可回归 | G 可回归评测 |

审计维度共 **A / B / C / D1 / D2 / D3 / E / F / G** 九条，每条独立给 ✅ PASS / ❌ FAIL，对象互不重叠：D1 管"有没有 QC 脚本"、D2 管"QC 的输入边界对不对"、D3 管"指令文本本身"，三者对象不同，不会把同一缺陷重复计两次。

**维度正交性边界（MECE 的"单一分类轴"）**：所有审计维度只沿**运行时工程属性**这一根轴——能否恢复、能否验证、能否复盘。**代码/结构风格类信号**（命名、步骤编号是否带小数、函数长度、复杂度、重复）属于另一根轴，一律转交通用 code review 或 CI linter，**不进 harness 审计**。把风格检查塞进某个 harness 维度，会让"恢复能力"被"命名整洁度"污染，这正是 2026 agent 评测框架反复强调要避免的维度交叉，也是 MECE 的硬约束。

**总评规则**：任一审计维度 FAIL → 总评 FAIL；全部 PASS → 总评 PASS。

每个维度对应一种典型 LLM 工作流失败模式。

---

## 维度 A：中间状态持久化（Intermediate-State Persistence）

**问题**：每一步执行完后，是否有**持久化 sidecar**（JSON / Markdown 片段 / 子目录）能让外部脚本/下次会话读到本步成果？这是 harness 工程的核心——状态不能只活在 LLM 上下文里。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 每个 Step/Task 都至少落一个**结构化 sidecar**（非 LLM 自由文本），字段定义明确 |
| ❌ FAIL | 以下任一：仅终态文件落盘、中间 Step 全在 LLM 上下文中传递、整个流程无任何分段中间产物 |

**反例**：
> "Step 3 提取分部数据"——只写"读出后填进某 dict 字段"，没说什么时候写盘、字段格式、缺失时怎么办（状态只活在 LLM 上下文里）

---

## 维度 B：断点续做（Resume-After-Interrupt）

**问题**：上次会话执行到第 4 步因任意原因中断（崩溃、超时、用户中止等），**这次会话能不能自动识别"已完成 Step 1-3"并从 Step 4 继续**，而不是从头再来？

| 等级 | 标志 |
|------|------|
| ✅ PASS | 有 manifest/status 命令（如 `<run-manifest> status`）扫描产物推断状态，**不依赖手动维护的状态文件** |
| ❌ FAIL | 以下任一：没有续做概念、重跑等于覆盖、仅靠"如已存在则跳过"的隐式约定而无统一状态查询入口 |

**反例**：
> 一气写完一个长 markdown，中途任意一步失败就要整篇重来（无 manifest 脚本，无法识别已完成步骤）

---

## 维度 C：部分重做（Partial Re-do）

**问题**：用户发现"Step 7 的 summary 写得不好，重跑 summary 就行"——能不能**只重跑这一步**而不动其他产物？

| 等级 | 标志 |
|------|------|
| ✅ PASS | SKILL.md 有"重做 X 步：删除 Y 文件"的明确表格，重做粒度 = 单个 Step |
| ❌ FAIL | 以下任一：没有部分重做概念、重做粒度只到整轮（`--force` 全重跑）、无"删除哪些文件触发哪步重做"的对应说明 |

**正例**：给出"删除哪些文件触发哪步重做"的对应表格，并注明跨 Step 联动（如"重做 Step 4 需联动 Step 5"）

---

## 基本面三「质检要程序化」拆出的三个审计维度

"质检要程序化"在审计时拆成三个**对象互不重叠**的维度，分别独立打分：D1 管 QC 脚本**存不存在**、D2 管 QC 脚本的**输入边界**、D3 管 **SKILL.md 指令文本本身**。同一个缺陷只会落进其中一个，不重复计分。

### 维度 D1：QC 存在性与覆盖率（QC Existence & Coverage）

**问题**：每步完成后，能不能用**纯脚本（非 LLM）**在 10 秒内验证产出合规？包括字段完整性、加总一致、单位、枚举值等机械检查。本维度只问"该有 QC 的地方有没有脚本"。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 关键 Step 都有配套 QC 脚本，退出码语义清晰，输出可机读；脚本命名与 Step 粒度一一对应 |
| ❌ FAIL | 以下任一：只有 LLM 自检 checklist 无脚本、只在终态有 QC、QC 覆盖率不足、退出码语义未定义、完全靠人眼或 LLM 复读；QC 脚本命名或职责混合多个 Step |

**关键判断**：QC 覆盖的是"有没有脚本"，不是"LLM 自检 checklist"。

**文档-实现脱节是 D1 的最高风险缺口**——SKILL.md 注释描述了某检查规则，但对应脚本里根本没有实现，等于零保障。典型例子：注释写了某渲染规则，但对应检查函数完全没有覆盖该场景。Step 5 实测是发现这类脱节的最可靠方法。

### 维度 D2：QC 依赖边界（QC Dependency Boundary）

**问题**：每个 QC 脚本是否只依赖**单个 Task 的产物**，不跨 Task 读取？本维度只问"已有 QC 的输入边界对不对"，不重复问 D1 的存在性。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 每个 QC 脚本只读取当前 Step 产物，或显式声明的上游依赖（入口声明、缺失即失败）；SKILL.md 无"禁止在 X 时机运行 Y"的警告语 |
| ❌ FAIL | 以下任一：联合 QC 存在（脚本跨读多个 Task 产物）；SKILL.md 中出现"禁止在 X 时机运行 Y"类警告语 |

跨 Step 的联合 QC 会制造两个问题：一是 Step A 结束后没有即时反馈窗口，Step A 的错误要等 Step B 完成才暴露；二是文档不得不补写"禁止在某时机运行"的警告，把时序约束从结构层降级到人工记忆。

**核心原则**：文档里出现"禁止在 X 时机运行 Y"是结构缺陷的信号。约束应当编码进 QC 脚本的输入声明（找不到依赖文件直接失败），而非依赖人工记忆。

**检查方法**：
```bash
# 检查 QC 脚本是否跨 Task 读取产物（文件读取模式按目标语言调整）
grep -rn "<file-read-pattern>" <qc-sources>
# 检查 SKILL.md 是否有时机警告语
grep -n "禁止在.*时机\|禁止在.*运行\|不.*时候.*运行" SKILL.md
```

**反例（联合 QC）**：
> 某联合 QC 同时读取 Step A 产物和 Step B 产物。Step A 结束时 Step B 产物不存在，脚本要么报错要么跳过检查，导致 Step A 的错误要等 Step B 完成后才暴露。SKILL.md 不得不写"禁止在 Step A 末尾运行此脚本"来补救。

**改进建议模板**：
- 发现联合 QC → 按 Step 边界拆分：每个 QC 只服务一个 Step 的即时反馈窗口
- 下游 Step 的 QC 如需交叉验证上游产物，可以读取上游产物，但须在脚本入口声明依赖并在文件缺失时给出明确报错
- 删除 SKILL.md 中一切形如"禁止在 X 时机运行 Y"的警告——结构正确后这种警告就不需要存在

### 维度 D3：指令极性（Instruction Polarity）

**问题**：给模型的指令本身也是一种产出。本维度的对象是 **SKILL.md 指令文本**（不是产物 QC，因此与 D1/D2 不重叠）。SKILL.md 中的**负向约束**（"禁止"、"不要"、"不得"）分两类，处理方式不同：

| 类型 | 例子 | 处理方式 |
|------|------|---------|
| **行为/风格约束**，有正向等价 | "禁止用某语言"、"不要写文件"、"不评估领域质量" | 改为正向表达，消除回弹风险 |
| **内容边界约束**，无正向等价 | "禁止在 section X 写入 Y 类内容" | 允许保留负向，但**必须有对应 QC 脚本强制执行** |

为什么行为/风格约束要正向化：根据 arXiv:2511.12381（2025 年 11 月），LLM 处理负向指令时会先在内部激活被禁止的概念再尝试抑制——抑制失败时，被禁止的行为反而更容易出现（「反讽回弹效应」）。内容边界约束描述的是"这个 section 不归属此类内容"，没有等价正向写法，因此允许保留负向，但仅靠文档说明不够，必须有 QC 脚本在产物生成后自动检出违规。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 行为/风格类负向约束均已正向化；内容边界类负向约束均有对应 QC 检查项 |
| ❌ FAIL | 以下任一：存在未改写的行为/风格类负向约束（含语言禁令）；内容边界类负向约束无 QC 配套 |

**检测方法**：
```bash
# 统计所有负向约束行
grep -n "禁止\|不要\|不得\|不允许\|避免\|don't\|do not\|never\|must not" SKILL.md

# 对每条负向约束判断：是行为/风格约束（有正向等价）还是内容边界约束（无正向等价）
# 行为/风格约束 → 提供正向改写建议
# 内容边界约束 → grep 对应 QC 脚本是否有实现；无实现 → D3 FAIL
```

**行为/风格约束正向改写参考**：
| 负向写法（有回弹风险）| 正向改写 |
|---|---|
| 禁止用某语言 | 所有输出使用目标语言 |
| 不要写文件 | 将结果输出到对话 |
| 不评估领域质量 | 评估范围限于 harness 工程质量 |
| 避免空泛断言 | 每个 finding 引用 SKILL.md 具体行号 |
| 不允许降级 | 严格执行强制路径 |

## 维度 E：可观测性 / Audit Trail（Observability）

**问题**：维度 A-D 解决"能不能恢复"，本维度解决**"事后能不能查为什么"**。当下游用户报告"某数据看起来不对"，能否追溯到具体哪一步、哪一次 LLM 调用、引用了哪个外部源？

| 等级 | 标志 |
|------|------|
| ✅ PASS | 每个 sidecar 都有 `generated_at` (ISO timestamp) + `source` / `inputs_hash` / `tool_versions` 等溯源字段；外部素材（PDF、网页）落盘在 `_sources/` 子目录 |
| ❌ FAIL | 以下任一：任何 sidecar 缺少时间戳或来源字段、只有终态产物有时间戳而中间 Step 无记录、引用外部素材但不存快照、事后无法 reproduce |

**反例**：
> 调用外部 API 抓取某数值写入产物，但不记录抓取时间——事后用户问"这个值是什么时候的"，无从查起

---

## 维度 F：失败处理契约（Failure-Handling Contract）

**问题**：Step 3 超时/校验失败/外部 API 返回空/QC 退出码 1 时，**SKILL.md 是否明确写了下一步怎么办**？是重试一次？整轮中止？降级到默认值继续？没有契约的话，LLM 会即兴发挥——这本身就是反 harness。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 关键失败点（外部数据缺失、QC 不过、用户中断）都有"如果 X 则 Y"的显式契约；QC 脚本退出码语义有定义（例如 exit=1 数值不符 / exit=2 schema 缺字段 / exit=3 违反硬约束） |
| ❌ FAIL | 以下任一：整个 SKILL.md 找不到"失败"/"错误"/"重试"/"中止"等措辞、QC 失败或外部依赖失败无处理契约、退出码语义未定义 |

**反例**：
> "用某数据源取数据"——不说取不到时降级到备用源还是中止；LLM 一遇错就乱猜数字

---

## 维度 G：可回归评测（Regression-Evaluability）

**问题**：维度 A-F 解决"单次跑能不能恢复、能不能查"；本维度解决**"整条工作流本身能不能被持续打磨"**。目标 skill 自己有没有一组固定的回归样本——标好哪些输入该触发、哪些不该触发、产出的关键属性应该是什么样——使得每次改动 SKILL.md 或 QC 后，能跑一遍立刻判断"变好还是变坏"？

这一维和维度 D1/D2/D3（程序化 QC）的区别在时间尺度：QC 管**每一次跑**，拦下这次的不合格产出；回归评测管**每一次改**，判断改动让整条线变好还是变坏。只有 QC 没有回归，作者不敢动这条线；只有回归没有 QC，单次错产出拦不住。

| 等级 | 标志 |
|------|------|
| ✅ PASS | 存在一组固化的回归样本/触发集（如 `evals/` 目录、fixtures、trigger 用例），覆盖触发边界与产出关键属性，且有可重复运行的入口（脚本或文档化命令）；改动后可一键回归 |
| ❌ FAIL | 以下任一：没有任何回归样本、"好不好用"只能靠人工感觉判断、改动后无法判断是变好还是变坏、触发边界无用例覆盖 |

**关键判断**：回归覆盖的是"有没有固定样本 + 可重复入口"，不是"作者声称测过"。

**与 evals 的关系（吃自己的狗粮）**：本仓库自身的 `evals/` 就是这一维度的示范——L1 lint（SKILL.md 自合规，零 LLM）、L2 behavioral（喂植入缺陷的工作流断言能抓出）、L3 trigger（三 skill 路由准确率与互斥性）。被审计的目标 workflow 应当建立同等性质的回归评测，哪怕只是一组手动触发的样本集。

**反例**：
> 一个多步骤 skill 改了 Step 4 的 prompt，作者只能凭"感觉这次输出顺一点"判断改动好坏，没有任何固定输入样本可以重跑比对——下次再改又得从头凭感觉。

**改进建议模板**：
- 无任何回归样本 → 建一组最小触发集：列出 N 个应触发输入 + M 个不应触发输入，记录每个的预期产出关键属性
- 有样本但无可重复入口 → 补一个运行脚本或文档化命令，使回归可一键执行
- 软判断维度（文笔、论点）无法机械断言 → 至少固化样本输入与人工评分基线，使每次改动有同一把尺子
